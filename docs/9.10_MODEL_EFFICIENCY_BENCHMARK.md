# 9.10 YAML 模型 Params、GFLOPs 与 FPS 评测

项目根目录脚本 `benchmark_yaml_model.py` 用于在固定 `640×640` 输入下评测任意模型 YAML。它可以加载对应的 `.pt/.pth`，并从 `crack-seg.yaml` 的 train、val 或 test 划分中读取真实图像。

## 指标口径

- `params_million`：模型原始参数量，不因 Conv-BN 推理融合而改变。
- `gflops`：使用项目验证代码相同的 Ultralytics/THOP 统计方法；如果 THOP 完全无法处理自定义算子，则尝试 `torch.profiler`。
- `model_forward_fps`：仅统计融合后 PyTorch 网络前向，不包括读图、预处理、NMS 和 mask 后处理。
- `end_to_end_fps`：包括 crack-seg 图像读取、resize/letterbox、网络前向、NMS、mask 后处理和 Results 构建，不包括结果图片保存。
- `peak_gpu_memory_mb`：整个评测期间 PyTorch 峰值显存。

Mamba selective scan 等自定义 CUDA 算子不一定能被 THOP 完整识别，因此论文报告 GFLOPs 时应统一使用同一个脚本和环境，并注明统计工具。FPS 应使用 `batch=1` 作为实时单图延迟主结果；较大 batch 的数值只能作为吞吐量实验，不能和 batch=1 直接比较。

## Windows PowerShell 推荐命令

```powershell
python benchmark_yaml_model.py --model-yaml "ultralytics/cfg/models/11/9.1-experiments/G01-z04-backbone-all-c3k2.yaml" --weights "output_dir/crack-seg-9.1/G01_crack-seg_seed0/weights/best_map50.pt" --data "crack-seg/crack-seg.yaml" --split val --device 0 --imgsz 640 --batch 1 --warmup 20 --forward-iters 100 --rounds 5 --images-per-round 0 --output-dir "benchmark_results/G01_640"
```

保存预测图片时额外添加：

```text
--save-predictions
```

FP16 测速时额外添加：

```text
--half
```

FP32 与 FP16 必须分别报告，不能把两种精度的结果放在同一比较列中。

## 不加载权重，只测 YAML 结构

权重数值通常不会改变规则网络的计算量和推理速度，因此也可以省略 `--weights`：

```powershell
python benchmark_yaml_model.py --model-yaml "ultralytics/cfg/models/11/9.1-experiments/G01-z04-backbone-all-c3k2.yaml" --data "crack-seg/crack-seg.yaml" --split val --device 0 --imgsz 640 --batch 1 --rounds 5 --output-dir "benchmark_results/G01_random"
```

但如果模块包含输入相关的动态执行路径，应加载实际训练权重，避免随机初始化导致执行分布不具有代表性。

## 输出文件

- `benchmark_images.txt`：每轮实际测速的 crack-seg 图像清单。
- `warmup_images.txt`：端到端预热图像清单。
- `benchmark_rounds.csv`：每一轮的耗时、延迟和 FPS。
- `benchmark_summary.csv`：Params、GFLOPs、FPS 均值/标准差、软硬件信息。
- `benchmark_summary.json`：与汇总 CSV 对应的结构化结果。
- `predictions/`：只在指定 `--save-predictions` 时生成。

为了公平比较所有模型，应固定相同的 GPU、PyTorch/CUDA 环境、图像子集、`imgsz=640`、batch、精度、warmup、rounds、置信度阈值和 NMS 阈值。测速期间应尽量关闭训练任务以及其他占用 GPU 的程序。
